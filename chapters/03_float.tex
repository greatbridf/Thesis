\chapter{RISC-V 启动与内存管理实现}\label{chap:riscv-mm}

启动和地址空间是移植工作最先遇到的部分。原 IA-32 版本 Unix V6++ 的启动过程依赖传统 PC 的实模式、保护模式和引导扇区加载机制，内存分配则保留了接近 Unix V6 的空闲块表思路；RISC-V/QEMU virt 平台的入口条件不同，内核通常由 QEMU 和 OpenSBI 共同引导，进入内核时已经处在 RISC-V 特权架构定义的执行环境中\cite{qemu_riscv_doc,opensbi_project}。本章只围绕后续 Trap、进程和用户程序运行所需的启动、页表和页资源基础展开，不把文件系统或完整内存管理策略作为单独重点。

\section{内核启动流程}

重构后系统通过 QEMU 的 \verb|-kernel| 参数加载 RISC-V 内核镜像，并使用 OpenSBI 作为固件层。OpenSBI 负责完成机器模式下的基础初始化，并将控制权转交给内核。内核入口由链接脚本 \verb|src/kernel-riscv64.ld| 指定，入口符号为 \verb|_start|，加载地址为 \verb|0x80200000|。该地址位于 QEMU virt 平台常用的 DRAM 区域内，也避开了 OpenSBI 自身占用的低地址空间。

链接脚本将内核划分为 \verb|.bootstrap|、\verb|.text|、\verb|.rodata|、\verb|.data| 和 \verb|.bss| 等段。其中 \verb|.bootstrap.entry| 保存最早执行的入口代码，\verb|.bootstrap.stack| 保存启动阶段使用的静态栈空间，\verb|__bss_start|、\verb|__bss_end| 和 \verb|__kernel_end| 等符号则供 Rust 代码在运行时定位 BSS 段和内核结束位置。相比原 IA-32 启动代码中较长的实模式到保护模式切换流程，RISC-V 版本的早期启动逻辑更集中，主要任务是建立 Rust 运行所需的最小执行环境。

内核入口 \verb|_start| 使用 Rust 的裸函数和内联汇编实现。入口代码先将栈指针 \verb|sp| 设置到预留的 bootstrap 栈顶，然后跳转到 \verb|riscv64_rust_entry|。OpenSBI 传入的 hart 编号和设备树地址保留在参数寄存器中，由 Rust 入口函数接收并输出到串口日志。本文讨论的启动路径围绕当前 QEMU 运行配置展开，重点是把控制流稳定带入 Rust 内核初始化阶段。

\verb|riscv64_rust_entry| 中的初始化顺序体现了内核模块之间的依赖。系统清零 BSS 段后，初始化页目录和用户页表并启用页表保护；串口随后接入，使后续步骤可以通过日志观察；物理页管理器、零号进程和 Trap 入口继续完成初始化，缓冲区、外部中断控制器和定时器再接入运行环境；文件系统超级块、根目录和控制终端位于更靠后的阶段。内核创建初始进程并进入调度器后，平台初始化才与 Unix V6++ 的用户态运行语义连接起来。

与原 IA-32 版本相比，RISC-V 版本的启动代码边界发生了明显变化。原版本需要在汇编中完成 BIOS 入口、磁盘扇区读取、GDT 设置、保护模式切换和跳转到高地址内核等步骤；重构后，机器模式下的大部分平台初始化由 OpenSBI 承担，内核侧的早期汇编主要集中在设置栈和跳转到 Rust 入口。启动阶段的工作重点由 PC 启动细节转向链接布局、页表建立和 Rust 裸机运行环境。

Rust 重写后，启动流程更多表现为入口函数中的一组有序调用。汇编部分主要负责设置栈和跳转入口，其余初始化逻辑由 Rust 表达。底层控制仍然保留，但初始化顺序、错误处理和调试输出更容易跟踪。对于本文实现而言，这部分工作不只是入口函数本身，还包括链接脚本、段符号、早期栈、串口日志以及后续子系统初始化顺序的配合。

\section{地址空间与页表设计}

RISC-V 64 位平台常用 Sv39 分页模式。Sv39 使用三级页表，虚拟地址被划分为多级索引和页内偏移，页表项中包含有效位、读写执行权限、用户位、全局位、访问位和脏位等标志\cite{riscv_unprivileged_20191213,riscv_privileged_20211203}。当前系统在 \verb|src/machine/page_table.rs| 中定义了 \verb|PageDirectory|、\verb|PageDirectoryEntry|、\verb|PageTable| 和 \verb|PageTableEntry| 等结构，用 Rust 类型对页表项编码、权限标志和页表数组进行封装。

系统地址空间需要同时满足内核访问自身代码、数据和管理的物理内存，用户程序获得从低地址开始的用户空间，以及内核访问 UART、PLIC、VirtIO 等 MMIO 设备这三类需求。当前页表据此建立低地址用户映射入口、物理内存恒等映射、内核高地址映射和 MMIO 映射。内核高地址从 \verb|0xc0000000| 开始，MMIO 区域从 \verb|0xf0000000| 开始，物理内存基址为 \verb|0x80000000|。

页表初始化由 \verb|init_page_directory| 和 \verb|init_user_page_table| 完成。前者清空根页表和二级页表，随后建立低地址页表入口、物理内存恒等映射和内核高地址映射；后者初始化用户页表数组，并将其挂接到低地址页表入口。系统随后调用 \verb|enable_page_protection|，将根页表物理页号写入 \verb|satp|，并执行 \verb|sfence.vma| 刷新 TLB，使新的地址翻译规则生效。

内核高地址映射采用大页映射与普通页表窗口结合的方式。对于大部分物理内存，系统以 2MB 为粒度建立直接映射，以减少页表项数量；对于需要细粒度切换的用户区窗口，则使用普通页表。当前代码中的 \verb|switch_user_struct| 会修改内核页表中固定位置的页表项，将当前进程的用户区物理页映射到内核可访问的窗口中，并刷新 TLB。这样可以保留 Unix V6++ 中类似 u-area 的访问方式，同时适配 RISC-V 的页表机制。

Rust 在页表实现中的作用主要体现在边界表达上。页表项权限通过 \verb|EntryFlags| 位标志表示，读、写、执行、用户、全局等权限组合比手写整数常量更便于检查；\verb|PageTable| 提供索引访问和迭代接口，页表初始化可以写成结构体数组的清空、挂接和映射，而不是分散的地址计算。底层编码仍需遵守 RISC-V 页表项格式，类型封装只是收窄了容易出错的操作范围。

\section{与原内存管理方式的对比}

原 IA-32/C++ 版本的页分配由 \verb|PageManager|、\verb|KernelPageManager|、\verb|UserPageManager| 和 \verb|Allocator| 共同完成。其核心数据结构是 \verb|MapNode| 数组，每个节点记录一段空闲区域的起始页号和长度，分配时从空闲表中寻找足够大的连续区间，释放时再将区间插入并尝试合并相邻空闲块。这一实现与 Unix V6 中 \verb|malloc|、\verb|mfree| 的思想接近，能够直观展示早期 Unix 内存管理的基本方法。

重构后的 RISC-V/Rust 版本仍然保留内核页和用户页分区管理的思想，但底层分配算法调整为 Buddy 分配器，并引入 \verb|PhysPage| 作为每个物理页的描述结构。相较于空闲块表，Buddy 分配器更适合按 2 的幂次申请和释放连续页，也便于与内核栈、用户进程地址空间和大对象分配统一起来。重构后的页资源不只以裸地址形式在模块之间传递，而是进一步封装为 \verb|KernelPages|、\verb|UserPages| 和 \verb|KernelStack| 等类型。

需要说明的是，C++ 本身也支持 RAII，但原 Unix V6++ 的内存管理实现主要服务于还原 Unix V6 的管理思想，代码组织上更多采用显式分配、显式释放和全局管理器。本文的 Rust 重构并不是否定这种设计，而是在跨平台移植过程中利用 Rust 的所有权、生命周期和 \verb|Drop| 机制，对资源管理边界进行重新表达。这样既保留了页资源来源与回收路径的可观察性，又减少了调用点遗漏释放或释放路径分散带来的维护压力。

\section{物理内存管理}

页表建立之后，内核需要管理可分配的物理页。当前系统在 \verb|src/mm/| 目录中实现物理页描述、内核页分配、用户页分配、内核栈和全局堆分配器等功能。物理页大小为 4KB，系统以 \verb|PhysPage| 描述每个页帧，并在 \verb|MemoryZone| 中维护页帧号与页描述结构之间的映射关系。当前实现将 64MB 物理内存纳入页帧管理，每个页帧对应一个 \verb|PhysPage| 结构。

\verb|init_page_managers| 是物理页管理的初始化入口。该函数通过链接脚本导出的 \verb|__kernel_end| 获得内核镜像结束地址，并按页对齐后作为可分配内核页区域的起点。系统将物理内存划分为内核页区域和用户页区域，前者主要用于内核对象、内核堆、设备缓冲区和内核栈，后者主要用于进程地址空间。两个区域分别由 \verb|KERNEL_PAGE_MANAGER| 和 \verb|USER_PAGE_MANAGER| 管理，底层均使用 Buddy 分配器。与原版本在头文件中写定内核页池和用户页池起始地址不同，当前实现更多依赖链接脚本导出的内核结束符号来确定可分配区域起点；内核镜像大小变化后，页分配区域可以随链接结果调整。

页分配接口设计区分 \verb|KernelPages| 和 \verb|UserPages|。两个类型共享底层 \verb|Pages| 泛型实现，但根据类型参数选择不同的分配器。\verb|Pages| 实现了 \verb|Drop|；封装对象释放时，其持有的物理页会归还给对应的 Buddy 分配器。内核资源生命周期较复杂，手工释放容易分散到多条路径。将页的所有权和释放动作绑定到类型，可以减少这类遗漏。进程地址空间、共享文本段和交换区仍然需要仔细处理所有权转移，类型封装只是提供了更清楚的边界。

这一点在进程相关资源中也比较明显。原版本在 \verb|Process::Expand|、\verb|Process::Exit| 和 \verb|ProcessManager::NewProc| 等路径中显式申请和释放用户页，并通过进程的 \verb|p_addr| 与 \verb|p_size| 记录进程图像位置；重构后，进程结构中的用户页、文本段引用和内核栈分别由对应字段持有，进程对象被移除或字段被替换时，相关资源能够沿着类型定义的生命周期释放。对于操作系统内核而言，这并不意味着不再需要设计释放路径，而是将释放路径从零散调用点收束到资源类型本身。

内核堆分配器由 \verb|allocator.rs| 实现，并通过 \verb|#[global_allocator]| 注册为 Rust 全局分配器。小于等于 2048 字节的分配请求由 slab 分配器处理，较大对象则从内核页分配器中申请连续页。这样，Rust 标准分配接口中的 \verb|Box|、\verb|Vec| 等容器可以在内核中使用，为进程表、文件对象、目录项缓存和其他动态结构提供基础。由于系统运行在 \verb|no_std| 环境下，这一全局分配器是 Rust 内核能够使用 \verb|alloc| crate 的前提之一。

进程内核栈也由内存管理模块统一分配。当前每个进程拥有独立的 \verb|KernelStack|，大小为 8 页，即 32KB。创建进程时，内核通过 \verb|KernelStack::new| 从内核页分配器申请栈空间，并通过物理地址到高地址虚拟地址的转换计算栈顶。独立内核栈配合 Trap 上下文和任务上下文切换，使每个进程在陷入内核时都有自己的内核执行空间，为后续进程调度和系统调用处理提供基础。
